# Design: 24x7ai v2 — Universal Agent Fleet Controller

## Problem Statement

24x7ai today is a working but tightly-coupled MVP orchestrator that processes a CSV of ideas through coding agents (Codex, Claude Code, OpenCode, custom) one at a time. It works, but it's locked to four agent modes, uses flat JSON for state, has no visibility into what agents are doing, and can't run persistent per-project improvement daemons alongside the main pipeline. The user wants to make it the universal open-source agent fleet controller: agent-agnostic, parallel, observable, and competitive with Cezar, osmove/backlog, and agents-cron.

## What Makes This Cool

You point 24x7ai at a CSV of 50 ideas, leave a $20 VPS running overnight, and wake up to 50 GitHub repos each with a working MVP, CI green, README written. While the main pipeline moves on to idea #11, persistent daemons for ideas 1-10 are independently watching GitHub issues, refining code, and shipping improvements. A TUI fleet controller shows you the entire swarm: what's building, what's refining, what's stuck, what shipped. One npm package, one VPS, zero cloud dependencies.

No existing tool does this. Cezar does parallel agent execution but requires human task assignment. osmove/backlog does task ingestion but has no persistent daemons. agents-cron does scheduled runs but is single-task. 24x7ai is the only tool where you feed in ideas and get back an autonomous software factory with a fleet controller.

## Constraints

- Must remain a single npm package installable via `npx 24x7ai`
- Single VPS deployment (no Kubernetes, no cloud services required)
- Agent-agnostic: must work with any CLI-based coding agent
- TUI + CLI only in v1 (no web UI)
- Apache-2.0 license
- Node.js 18+ runtime requirement stays

## Premises

1. **Agent-agnostic via adapter pattern with Otari as default model gateway.** Each CLI agent gets a thin TypeScript adapter that normalizes invocation, prompt passing, and completion detection. Otari (Mozilla's open-source model gateway) is configured as the default model routing and governance layer for all agent runs to provide a unified OpenAI-compatible endpoint, virtual API keys, pre-execution budget caps, provider failover, and token spend tracking across the fleet.
2. **Per-project daemons run on schedule, not literally 24/7.** Each daemon wakes up, checks for GH issues, picks one improvement, runs the agent, commits, sleeps. Controlled via fleet controller (start/stop/pause per project).
3. **Fleet controller = TUI + CLI.** TUI shows project list, main pipeline progress, per-project daemon status, last commit, stuck detection. CLI commands for start/stop/pause/reprioritize/kill.
4. **SQLite replaces flat JSON for state.** One DB for the whole fleet: project status, agent runs, commit history, error logs. Makes TUI fast and fleet queryable.
5. **flock + git worktrees for concurrency.** Main pipeline holds one flock. Each daemon holds its own. Configurable max-parallel setting bounds total concurrent agents.
6. **npm distribution, Apache-2.0 license.**

## Approaches Considered

### Approach A: Evolutionary Refactor
Extend the current Bash/Node.js harness incrementally. Add adapter pattern, migrate to SQLite, add daemon lifecycle, build TUI on top. Each piece ships standalone.
- Effort: M (2-3 weekends). Risk: Low.
- Pros: Zero breakage for existing users, each feature ships independently.
- Cons: Shell script complexity grows past 10 daemons, harder to attract contributors to Bash+Node hybrid.
- **Ruled out:** User chose clean-room rewrite for maximum contributor appeal and single-language simplicity.

### Approach B: Clean-Room TypeScript Rewrite (CHOSEN)
Rewrite from scratch in TypeScript. Proper adapter registry, SQLite via better-sqlite3, daemon manager with process supervision, TUI via ink. Shell scripts become generated execution artifacts, not source code.
- Effort: L (4-6 weekends). Risk: Medium.
- Pros: Type-safe adapter system, single language, cleanest extension points for community adapters.
- Cons: Nothing ships until core is usable, more dependencies.

### Approach C: Hybrid TypeScript Core + Shell Execution
TypeScript for orchestration, shell for agent execution. Two-language boundary.
- **Ruled out:** User preferred single-language purity of full TypeScript rewrite.

## Recommended Approach

**Approach B: Clean-Room TypeScript Rewrite** — chosen by the user for single-language contributor friendliness and clean architecture. The "1 harness, 1 vps, 1 .sh" tagline evolves to "1 package, 1 vps, 1 command."

### Key Architectural Decisions

**Adapter Interface:**
```typescript
interface AgentAdapter {
  name: string;
  detect(): Promise<boolean>;          // Is this agent installed?
  invoke(opts: InvokeOptions): Promise<AgentResult>;
  parseStatus(projectDir: string): Promise<ProjectStatus>;
}

interface InvokeOptions {
  projectDir: string;
  prompt: string;
  timeout?: number;
  env?: Record<string, string>;
}

interface AgentResult {
  exitCode: number;
  duration: number;
  commits: string[];       // SHAs produced
  filesChanged: string[];
}
```

**Daemon Lifecycle:**
```
IDLE -> SCHEDULED -> RUNNING -> IDLE (success)
                            \-> ERROR -> BACKOFF -> SCHEDULED
                            \-> STUCK -> NOTIFIED -> IDLE (manual restart)

States controlled via: 24x7ai daemon start/stop/pause/resume <project>
```

**SQLite Schema (core tables):**
```sql
CREATE TABLE projects (
  id INTEGER PRIMARY KEY,
  slug TEXT UNIQUE NOT NULL,
  idea TEXT NOT NULL,
  sl_no INTEGER NOT NULL,
  source_csv TEXT,
  mvp_complete BOOLEAN DEFAULT FALSE,
  daemon_active BOOLEAN DEFAULT FALSE,
  daemon_schedule TEXT DEFAULT '*/30 * * * *',
  created_at TEXT DEFAULT (datetime('now')),
  updated_at TEXT DEFAULT (datetime('now'))
);

CREATE TABLE agent_runs (
  id INTEGER PRIMARY KEY,
  project_id INTEGER REFERENCES projects(id),
  adapter TEXT NOT NULL,
  prompt TEXT,
  exit_code INTEGER,
  duration_ms INTEGER,
  commits_produced INTEGER DEFAULT 0,
  files_changed INTEGER DEFAULT 0,
  error TEXT,
  run_type TEXT CHECK(run_type IN ('mvp', 'daemon', 'manual')),
  started_at TEXT DEFAULT (datetime('now')),
  finished_at TEXT
);

CREATE TABLE daemon_state (
  project_id INTEGER PRIMARY KEY REFERENCES projects(id),
  status TEXT CHECK(status IN ('idle','scheduled','running','error','stuck','paused')),
  last_run_id INTEGER REFERENCES agent_runs(id),
  next_run_at TEXT,
  consecutive_errors INTEGER DEFAULT 0,
  backoff_until TEXT,
  updated_at TEXT DEFAULT (datetime('now'))
);
```

**Stuck Detection:**
A daemon run is "stuck" when:
- Agent process runs longer than `stuckTimeout` (default: 30 min)
- Last N runs (default: 3) produced zero commits and zero file changes
- Agent exits with the same error N times in a row

On stuck: daemon moves to STUCK state, fleet controller shows a warning, optional notification (webhook/email future feature).

## Open Questions

1. **Otari integration depth:** Settled — Otari is default out of the box. All agent adapters route through Otari's OpenAI-compatible proxy by default, enabling unified token budgets, virtual keys, and automatic model failover across providers.
2. **GitHub issue ingestion:** Should daemons automatically pick up GH issues as prompts, or should users curate which issues become agent tasks? Recommendation: auto-ingest with a label filter (e.g., `agent-task`).
3. **Notification system:** When a daemon gets stuck or an MVP completes, how should the user be notified? Options: TUI-only (default), webhook, ntfy.sh, email. Recommendation: TUI + optional webhook in v1.
4. **Agent output validation:** Beyond checking for commits and .agent-status.json, should 24x7ai validate that the agent's work actually compiles/passes tests? Recommendation: defer to v2.1 — let the agent handle its own validation via its prompt.
5. **Multi-VPS / distributed fleet:** Out of scope for v1, but the SQLite schema should not preclude a future PostgreSQL migration for multi-node fleets.
