# Milestone 002: 24x7ai Agent Runtime & Lifecycle

You are the principal TypeScript engineer for 24x7ai.

## Objective

Build a reusable agent runtime capable of creating, configuring, executing and managing independent AI agents through our existing Otari provider adapter.

Kimi K3.1 Pro is the primary model for all three initial agent roles.

## 1. Repository inspection

Before coding:
- Inspect the existing repository.
- Review the Otari provider implementation.
- Review config/models.json.
- Identify existing interfaces, conventions and tests.
- Preserve the existing architecture.
- Report the implementation plan and files to be changed.

## 2. Agent abstraction

Create a reusable Agent interface.

Each agent must support:

- Unique ID
- Logical role
- Model resolution
- System instructions
- Task-specific context
- Execution timeout
- Structured result
- Error handling
- Cancellation where feasible

Suggested interface:

interface Agent {
  id: string;
  role: "architect" | "builder" | "tester";

  run(task: Task): Promise<AgentResult>;
}

Adapt this interface to the existing codebase rather than blindly copying it.

## 3. Initial agent definitions

Architect:
- Model: config/models.json → architect
- Receives raw ideas or tasks.
- Produces structured plans.

Builder:
- Model: config/models.json → builder
- Receives implementation tasks.
- Produces structured implementation results.

Tester:
- Model: config/models.json → tester
- Receives test and verification tasks.
- Produces structured test reports.

For now, all three use Kimi K3.1 Pro.

Do not implement their full autonomous workflows yet.

## 4. Lifecycle management

Implement these states:

idle
queued
running
completed
failed
cancelled
timed_out

Requirements:
- Valid state transitions.
- Execution timestamps.
- Error capture.
- Timeout handling.
- Cancellation support.
- Retry support with configurable limits.
- No duplicate execution of the same run.
- Correct cleanup after failures.

## 5. Execution engine

Implement:
- Agent registry.
- Agent factory.
- Task dispatcher.
- Execution manager.
- Model selection through existing Otari adapter.
- Structured logging.
- Run IDs and correlation IDs.

Keep provider logic separate from agent logic.

## 6. Persistence

Inspect existing SQLite implementation first.

Persist:
- Agent definitions.
- Execution runs.
- Run statuses.
- Start/end timestamps.
- Errors.
- Execution metadata.

Do not duplicate existing tables or storage abstractions.

## 7. Concurrency

Support:
- Configurable maximum concurrent agents.
- Task queue.
- Per-agent execution isolation.
- Graceful shutdown.
- No uncontrolled parallel requests.

Do not implement distributed scheduling yet.

## 8. Testing

Write tests for:
- Agent creation.
- Model resolution.
- Successful execution.
- Failed execution.
- Timeout.
- Cancellation.
- Invalid state transitions.
- Retry limits.
- Concurrent execution limits.
- Persistence and recovery.

Mock Otari for unit tests. Do not consume API credits unnecessarily.

## 9. CLI integration

If compatible with the existing CLI, add:

24x7ai agents list
24x7ai agents show <id>
24x7ai runs list
24x7ai run status <run-id>

Avoid breaking existing commands.

## Constraints

- TypeScript and npm.
- Apache-2.0.
- Reuse the existing Otari integration.
- No hardcoded API credentials.
- No unnecessary dependencies.
- No unrestricted shell execution.
- No destructive changes.
- Keep modules independently testable.

## Acceptance criteria

1. Three logical agents can be instantiated.
2. Each resolves its model from config/models.json.
3. Each can execute through the Otari adapter.
4. Agent lifecycle transitions are enforced.
5. Runs are persisted.
6. Concurrency limits work.
7. Timeouts and errors are handled.
8. Tests pass.
9. Existing milestone 001 functionality remains intact.

First inspect and report the repository findings and implementation plan. Then implement the milestone, run tests and summarize changed files.

Do not start milestone 003 automatically.
